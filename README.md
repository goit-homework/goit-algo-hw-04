## Завдання 1 — рекурсивний копіювач файлів

Проходить рекурсивно по `source`, копіює кожен файл у `dest/<розширення>/`.

```bash
python3 task1.py <source> [dest]
```

Якщо `dest` не вказано — використовується `./dist`.

Особливості:

- розширення регістронечутливе (`a.JPG` і `b.jpg` обидва в `jpg/`);
- файли без розширення → `no_ext/`;
- колізії імен розв'язуються суфіксом `__1`, `__2`...;
- симлінки пропускаються (щоб не зациклитись);
- `PermissionError` / `OSError` ловляться, скрипт іде далі;
- в кінці — підсумок по кожному розширенню.

## Завдання 2 — сніжинка Коха

```bash
python3 task2.py
```

Питає рівень рекурсії. Рекомендований діапазон 3–6. Якщо ввести >6 —
перепитає підтвердження, бо кількість сегментів = `3 * 4^level`
(level 7 = ~50k сегментів, малювання довге).

Управління у вікні:

- скрол колеса миші — зум (відносно курсора);
- ліва кнопка + перетягування — пан;
- клавіша `q` — вийти.

## Завдання 3 — порівняння сортувань

```bash
python3 task3.py
```

Тестує три алгоритми (insertion sort, merge sort, Timsort через `sorted()`)
на чотирьох розподілах (`random`, `sorted`, `reverse`, `nearly_sorted`)
з розмірами `100, 1000, 5000, 10000, 100000`. Час вимірюється через `timeit`.

Insertion sort на 100k пропускається — O(n²) дав би ~140с на запуск, а гап
між алгоритмами вже добре видно на 10k.

Виведення: ASCII-таблиця в консоль + графік `benchmark.png` (log-log).

### Результати (приклад прогону, мс на запуск)

| dataset       | size   | insertion | merge  | timsort |
|---------------|--------|-----------|--------|---------|
| random        |  10000 |   1410.45 |  13.87 |    0.74 |
| random        | 100000 |      skip | 186.66 |   11.13 |
| sorted        |  10000 |      0.81 |   9.60 |    0.04 |
| sorted        | 100000 |      skip | 112.71 |    0.42 |
| reverse       |  10000 |   2688.62 |   9.66 |    0.04 |
| reverse       | 100000 |      skip | 111.25 |    0.43 |
| nearly_sorted |  10000 |      0.82 |   9.25 |    0.10 |
| nearly_sorted | 100000 |      skip | 106.52 |    1.00 |

### Висновки

**Insertion sort** має складність O(n²) у середньому/найгіршому випадку
і O(n) у найкращому (вже відсортовані дані). Це чітко видно: на `random` і
`reverse` 10 000 елементів він вимагає секунди, тоді як на `sorted` і
`nearly_sorted` справляється за міллісекунди — внутрішній цикл просто
не виконується, бо `key` уже на місці.

**Merge sort** працює стабільно за O(n log n) незалежно від типу даних.
На 10 000 елементів — ~10 мс на всіх розподілах. Передбачуваний,
але дорогий через постійне виділення нових списків (наша Python-реалізація
не in-place).

**Timsort** (`sorted()`) — переможець у всіх категоріях, часто на 1-2 порядки.
Він поєднує найкраще з обох світів:

- це адаптивний merge sort, який знаходить уже відсортовані піддіапазони
  ("runs") і зливає їх замість того щоб сортувати з нуля. Тому на `sorted`
  і `nearly_sorted` він майже миттєвий (близько до O(n));
- для коротких runs використовує insertion sort, який практично не має
  overhead на малих масивах;
- реалізований у C — без накладних витрат Python інтерпретатора.

На `random` 10 000 елементів Timsort швидший за наш merge sort у ~18 разів,
за insertion — у ~1800 разів. На `nearly_sorted` різниця ще драматичніша:
Timsort бачить що дані майже відсортовані і виконується за O(n).

На 100 000 елементів адаптивність Timsort стає ще помітнішою: на `random`
~11 мс, а на `sorted` — лише 0.4 мс, тобто ~26× різниці залежно від
структури вхідних даних. Merge sort, натомість, дає стабільні ~110 мс
скрізь, бо завжди робить однакову роботу.

**Висновок:** писати власне сортування для прод-коду немає сенсу. Стандартний
`sorted()` / `list.sort()` випереджає чесно реалізовані O(n log n) алгоритми
завдяки C-імплементації та адаптивності до структури вхідних даних.
Самописні сортування корисні тільки як навчальний матеріал — щоб зрозуміти
*чому* Timsort такий швидкий.
